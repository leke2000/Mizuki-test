这周（9/21–9/24）四天，三天在折腾五子棋，一天在写文档和做重构。记一篇周报，把技术和踩坑都留个档。

## 一、五子棋：从人机对战到群里约战

### 1. 先有引擎，再有界面

对弈本体是单文件网页版，15×15、触屏落子、离线可玩。AI 强度靠三样东西堆起来：

- **棋型表打分 + αβ 迭代加深**：先算分值再搜索，用迭代加深保证任意时限内都有招可下；
- **强制挡点**：对手冲四时必须堵，绝不让搜索去权衡「值不值」；
- **静态搜索（含 VCF）**：叶子节点继续把连续冲四算完，避免地平线效应——**这个坑很典型**：不做延伸的话，AI 会因为看不到下一步的杀棋而变保守，最后走出一堆和棋。做完对练验证（贪心/2 层前瞻对手各打了 8~12 局）才确认 0 负 0 平。

留给玩家的容错是 2 次悔棋，且只能悔自己的棋。

### 2. 联机：全程没有后端

这块是这周真正花时间的部分。思路是借现成的公共通道，把「房间」这件事做成一个自洽的协议：

| 问题 | 做法 |
| --- | --- |
| 怎么约战 | 4 位房间号（去掉易混字符），分享链接形如 `?r=ABCD`，群里点开自动进房 |
| 怎么通信 | 页面内置最小 MQTT 客户端 + ntfy.sh 兜底，按固定优先级顺序探测 broker |
| 两边不在同一通道怎么办 | 消息里带通道号，发现不一致就往小号通道靠（自愈） |
| 消息重复/断线 | 按消息 id 去重，断线自动重连 |
| 角色怎么分 | 1 号位房主（先手）、2 号位对手（后手），第 3 人起自动变观众，可发弹幕 |
| 怎么保证两边局面一致 | 房主广播权威局面；悔棋要对方同意，同意后**两边同时撤两手** |

踩到的坑值得单独记一条：**不同的公共 broker 之间是不互通的**。一开始以为是协议 bug，排查后确认是「两个人压根没连到同一个 broker」。解法不是加重试，而是把「谁跟谁在一起」从人肉约定改成自动收敛——固定探测顺序 + 通道号对齐，谁先发现不一致谁往小号靠。

### 3. 共享排行榜

没后端还想做「全网共享榜」，思路是把一个固定房间 `TOP1` 当成共享文档：用 MQTT 的 retain（或 ntfy 的缓存）实现「最后写入者覆盖」。晚到的人连上就能读到榜，不需要任何服务器。积分口径也写死了：胜 ×10 + 最快取胜奖励 − 失误 ×1.5 + 平 ×2，同昵称取高分。

> 这套东西本质上是「用公共消息通道当数据库」，适合玩具项目，不适合有强一致要求的场景——留着当个思路参考。

## 二、大屏项目：使用数据的关联键从「名称」改成「ID」

这周的正式工作是一笔重构：大屏的使用数据以前拿**医院名称**当关联键，这周统一改成**医院 ID（hospital_id）**。三个仓库要一起动：

- **管理后台表单**：去掉医院名称输入框，只提交医院 ID，名称由后端带出；
- **后端查询**：关联键换成 ID，名称按 ID 查医院表；
- **大屏展示**：地图点位返回医院 ID，月度数据按 ID 查询。

改完最花时间的**不是改代码，而是验证「不该变的东西」**：

| 验证项 | 期望 | 结果 |
| --- | --- | --- |
| 统计口径 | 数字不变 | ✅ |
| 地图点位 | 数量与位置不合并、不错乱 | ✅ |
| 名称不一致的历史数据 | 不再漏数据 | ✅ |
| 空值/重复数据 | 不出现空名称、不错位 | ✅ |

顺便修了一个 CI 上的坑：**pnpm 的构建脚本白名单必须写进仓库配置**（`pnpm-workspace.yaml` 的 `allowBuilds`），否则在无人值守的流水线上会卡在交互式确认那一步，表现就是 Jenkins 构建失败但本地一切正常。

另外一条经验是发布顺序：**加字段和删旧字段必须分阶段**。旧代码还在读老字段的时候先把字段删了，线上会立刻挂——「先改库还是先发代码」这个问题要先想清楚再动手。

## 三、一份新需求的「复用盘点」

拿到一份新需求文档，我没有直接估工期，而是**逐条对着现有代码库盘点**，把每个需求块分成三类：

| 分类 | 占比 | 说明 |
| --- | --- | --- |
| 可直接复用 | 约 40% | 提示词配置、大模型日志、多轮会话持久化、语音接入、医生端回写等，现网已有实现 |
| 需要改造 | 一部分 | 已有链路能跑，但不满足新要求：缺题型、缺轮数控制、缺预警、报告不回写等 |
| 完全新建 | 一部分 | 预约/号源模型、患者账号体系、患者端 H5——这些是零基础 |

这份盘点最有价值的一条结论不是工作量，而是：**新需求和一条已上线的链路正面冲突**。所以要做的第一个决策不是排期，而是「改造还是重写」——不定这个，后面一定会长出两套并行实现。

顺手记一个读代码的方法：**从界面反推链路**。拿已经做完的需求练手，从「页面上看到的一个数字」往回追到接口、Controller、表结构，一条链画一遍，比从头读文档快得多。

## 四、给自己写了一份分阶段学习计划

给大屏这套东西写了份学习计划，原则是**每个阶段都以「能独立完成某事」为验收**，而不是「看过/知道」：

1. **环境与排障**：能从零把三端跑起来；页面出问题时能判断是前端页面、前端服务、后端接口还是数据库依赖的问题；
2. **Git 与 MR 协作**：独立走完「拉 master → 建分支 → 提交 → 同步 → 建 MR → 评审 → 合并清理」，重点练冲突处理和分支落后；
3. **读代码、画链路**：拿到需求能画出「需求 → 组件 → 接口 → 表」并说出改哪几个文件；
4. **开发与验证**：会造测试数据、会做防回归验证（「我不该影响的东西」也要证明没坏）；
5. **数据库变更与发布**：会写幂等的脚本、会走发布、知道怎么回滚。

## 五、这周记下来的几条

- **排查先分层**：页面 → 前端服务 → 后端接口 → 数据库/中间件，永远从最外层往内推，别一上来就怀疑代码；
- **改动先问「我不该影响什么」**，然后真的去验证它——需求里写「不改动范围」的地方，就是评审会盯的地方；
- **动数据三件套**：备份 → 干跑核对 → 可回滚；
- 构建「成功」不等于产物更新，要核对产物时间戳；
- CI 里的任何交互式确认，都得改成仓库里的配置文件；
- 关联键用 ID 别用名称——名称会变，一变就要全库同步。
